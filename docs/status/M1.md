# M1: Loader, reference engine, logtest
Machine: Ryzen 7 5700X desktop (Windows 11, Docker Desktop engine 29.8.2, cargo 1.99.1)   Date: 2026-11-22

## Built

- Workspace (Apache-2.0, `publish = false`, `unsafe_code = "forbid"` in
  every crate, no `cfg(target_os)`), crates from SPEC §5 that M1 needs:
  - `rulelanes-model`: events, decoded fields, outcomes, compiled decoders,
    rules and rule tree; the `osmatch` and `osregex` matchers; PCRE2-style
    patterns through `fancy-regex` (MIT); IPv4 lists.
  - `rulelanes-syntax`: a reader for Wazuh's XML dialect (several roots,
    `\<` escapes, `<var>`), decoder and rule loading for the M1 subset in
    `docs/syntax.md`, pattern parsing, strict load (`load_files`) and
    lenient load with a report (`check_files`).
  - `rulelanes-engine`: pre-decode (syslog header forms), decode (decoder
    lists, children, sibling multi-regex, offsets, JSON plugin), match
    (rule tree, category, children by level, `noalert`, `$(field)` in
    descriptions, `log_alert_level`).
  - `rulelanes-oracle` (dev-only): drives `wazuh-logtest` through the
    documented API with an isolated ruleset, records and reads fixtures,
    compares; the corpus generator; the `rulelanes-oracle` tool
    (`corpus`, `record`, `compare [--live]`).
  - `rulelanes`: CLI `logtest` and `check`.
- Test ruleset written here: `testdata/ruleset/` with 39 decoders (25
  decoder names) and 86 rules (85 rule IDs plus one `overwrite`), IDs
  880100-880982 plus category roots 1-3, clear of the UniFi range.
- Generated corpus: `testdata/corpus/corpus.log`, 1,200 lines from a fixed
  seed (30 line templates, including near misses and undecodable lines).
  In the oracle results 1,067 lines decode, every line reaches a rule, 603
  alert, and 73 of the 85 rule IDs fire at least once.
- Recorded oracle output: `testdata/fixtures/r1-wazuh-4.14.10.jsonl`
  (header names "Wazuh v4.14.10"), so `cargo test` is meaningful offline.
- R2 fixtures: `testdata/unsupported/` (10 files).
- `oracle/logtest.py` now waits and retries on HTTP 429 (the API's
  default 300 requests per minute); `oracle/restore-ruleset.sh` puts the
  stock ruleset configuration back after an interrupted run.

## How the oracle is isolated

`Oracle::run_isolated` copies the decoders and rules under test into
`/var/ossec/etc/rulelanes/`, backs up `ossec.conf` to
`ossec.conf.rulelanes-stock`, rewrites only the `<ruleset>` block to load
just those two directories, runs the lines through `PUT /logtest` (a new
logtest session reads the ruleset when it starts, so analysisd is not
restarted), then restores `ossec.conf` and removes the files, also on
error. A lock directory in the container serialises runs.

## Corrections and deviations

- R1 is checked with an isolated ruleset (only `testdata/ruleset/`), not
  with the stock ruleset loaded beside it: stock decoders and generic stock
  rules would otherwise take some of the test lines, and the engine does
  not load the whole stock ruleset in M1.
- The alert flag depends on `log_alert_level` (3); the engine takes it as
  configuration with Wazuh's default (`Engine::with_alert_level`).
- `<field>` cannot name a static field; three test rules were rewritten
  (`match`/`regex`) after the oracle refused them.
- osregex `)(` adjacency and some PCRE2 constructs are refused (see
  `docs/syntax.md`); two test decoders were rewritten after the oracle
  showed Wazuh does not match `(\p+)(\w+)`.
- Pre-decoding supports the syslog timestamp forms in the first branch of
  Wazuh's header parser (BSD, ISO 8601 variants, `yyyy Mmm dd`); xferlog,
  snort, suricata, apache, AIX and macOS ULS headers are treated as "no
  header". Not part of R1 in M1.
- The JSON decoder is tested on objects, nested objects, strings, numbers,
  booleans and an array of strings; `null`, nested arrays and number
  formatting edge cases are not covered by the corpus.
- `if_group` is matched as a whole group name (case-insensitive); only one
  test rule uses it.
- **Source consulted.** To learn semantics the docs leave out (decoder
  order, rule tree order, osregex matching, header parsing), I read the
  Wazuh 4.14.10 C source (GPL-2.0) outside the repository. No code was
  copied; the Rust implementation is written separately and every
  behaviour it relies on is checked against `wazuh-logtest`. The
  character-class tables of osregex were taken from Wazuh's tables (facts,
  listed in `rulelanes-model/src/pattern.rs`). Evan may want to judge
  whether this is acceptable for an Apache-2.0 repo.
- No performance figures: nothing was measured.

## Incident: the oracle was left isolated after the Docker restart

The session was disconnected during a `record` run, and Docker Desktop was
restarted. The interrupted run had left `ossec.conf` with the isolated
`<ruleset>` (only the rulelanes test files), and the manager came back up
with that configuration, so for a while the live manager analysed with only
the rulelanes test ruleset (no stock rules, no UniFi rules). Found when the
session resumed; fixed by restoring `ossec.conf` from the backup and
restarting the manager (now `oracle/restore-ruleset.sh`). Checked after:
stock `sshd` line gives rule 5710 and the UniFi sample gives rule 100301.
No agents or syslog sources send to this manager, so no events are known to
have been affected.
