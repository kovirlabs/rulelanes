# M2: Staged pipeline and benchmark
Machine: Ryzen 7 5700X desktop (8 cores / 16 threads, Windows 11 Home build 26300.10075, bare metal, rustc 1.99.1; Docker Desktop engine 29.8.2, WSL 2 kernel 6.18.58.1)   Date: 2026-11-23, updated 2026-11-24 (R8 work)

**The gate is not reached.** R3 and R4 pass. R8: match now allocates
nothing after warm-up and decode 0.22 times per event, all of it in
PCRE2 captures and JSON arrays (was 13.1 and 6.7); not zero, so R8's
no-lock rule still fails for decode. R5 still fails, but narrowly for
evenly spaced arrivals: after the R8 work (2026-11-24) capacity rose
from about 0.78 to 1.9 million events/s, p99 at 90% load is 9 to 28 µs
(was up to milliseconds), and the R5 ratio is 2.16 and 3.16 for even
arrivals (rule: at most 3) and 5.1 and 4.1 for Poisson. R6 is measured
for throughput only (2026-11-23). Every load figure here needs a repeat
on Linux before it is final.

## Built

- **`rulelanes-pipe`**: the reference engine's steps on four
  `stagelanes-pipe` stages (`stagelanes` `main` at `3f27631`, path
  dependency, Apache-2.0):

  ```
  Feeder -> parse -> decode -> match -> write -> Sink
  ```

  - parse: checks the input and rejects it, counted by reason (`empty`,
    `too_long` over `Config::max_line`, `not_utf8`, `unknown_source`), or
    pre-decodes it (`rulelanes_engine::predecode`).
  - decode and match: `rulelanes_engine::decode` and `matcher`, each stage
    with its own clone of the `Engine`, so no compiled pattern is shared
    between threads.
  - write: builds the `Outcome` and hands it to a `Sink`, in input order.
  - Links of 256 slots, batches of 32, idle stages spin. A full link makes
    the sender wait, back to the `Feeder`; nothing is dropped. The feeder
    counts how often it found the link full.
  - `Report::balanced()`: sent = received = written + rejected, and every
    stage saw the same count.
  - Input lines are `Arc<[u8]>`, so a receiver hands a line over without
    copying.
- **`rulelanes-bench`**: capacity (unpaced, median of three trials), then a
  fresh pipeline per arrival pattern (evenly spaced, Poisson) and load
  (default 50% and 90% of the capacity just measured); latency from the
  scheduled arrival time to the write stage; R5 ratio per pattern;
  allocations per input per stage (`stagelanes_mem::CountingAlloc`); the
  single-threaded reference engine's rate for context. Stages pinned to
  logical CPUs 2, 4, 6, 8 (first core left to the OS), feeder on 10. Run
  files record the program by file name and mask the home directory. An
  optional `mimalloc` feature (MIT, off by default) swaps the allocator for
  an experiment.
- **`oracle/analysisd-bench.sh`** with `oracle/analysisd_bench.py` (R6):
  in the oracle container only, installs `testdata/ruleset` alone (the R1
  isolation), sets `analysisd.state_interval=1`, restarts the daemons
  (`wazuh-control restart`), sends the corpus in a loop from N processes
  to `analysisd`'s local datagram socket in the standard Wazuh message
  format (`1:source-N:<line>`), samples `wazuh-analysisd.state`, restores
  everything (also on error) and writes a run file.
- `Engine` is `Clone` and exposes `alert_level()`.
- `CLAUDE.md`: Evan's push/PR rule of 2026-11-23, no local paths in run
  files, `stagelanes-pipe` is on `main`, bench commands.
- Dependencies: `stagelanes-arch`, `-mem`, `-pipe` (Apache-2.0, path);
  optional `mimalloc` 0.1.52 and `libmimalloc-sys` 0.1.49 (MIT) with `cc`
  1.11.3, `find-msvc-tools`, `shlex` (MIT OR Apache-2.0). All GPL-3.0
  compatible.

- **R8 work (2026-11-24)**, seven commits from `7cbd954` to `b4b81be`:
  - Patterns match without allocating: `osmatch` compares
    case-insensitively in place; `osregex` writes captures into a reused
    buffer (`Pattern::exec_into`) or a stack buffer (`is_match`,
    `find_end`); prematch asks only for the match end (`find_end`), which
    for PCRE2 uses fancy-regex's `find` and builds no capture set for
    patterns it hands to the regex crate.
  - The engine's steps have in-place forms: `predecode_into`,
    `decode_into` (with `decode::Scratch`), `match_into` (with a pool of
    description buffers). The old functions wrap them, so the reference
    engine and the pipeline still run one code path.
  - Model: an `Event`'s timestamp, hostname and program name are ranges
    into its line; its location is an `Arc<str>` per source;
    `DecodedEvent` keeps its field strings between events; decoder names
    and rule groups are `Arc`-shared.
  - The JSON plugin checks the text once with serde_json's parser and
    streams it into the event; an object with a duplicate key still goes
    through a `serde_json::Value` (the reference path), and an array's
    text is still printed from a `Value`. Equal to the `Value` path on 16
    written cases and 5,000 generated objects.
  - The pipeline circulates `POOL` (1,024) items: write hands each back to
    parse over a return link, so buffers are reused (SPEC §5's pooled
    items, in this form). `Report::pool_waits` counts parse waiting for
    an item; the bench records it.
  - `tests/r8_alloc.rs` asserts, after a warm-up pass over the corpus:
    match makes no allocation; decode allocates only for decoders whose
    regex is PCRE2 or for JSON events holding an array (1,056 of 1,200
    events allocate nothing). Per decoder: rl-kv 3.00, rl-dns 1.00,
    rl-web 0.81, rl-json 0.68 per event, every other decoder 0.
  - New direct dependency: `serde` 1.0.229 (MIT OR Apache-2.0), already in
    the tree through `serde_json`.

**After the R8 work (2026-11-24, `2026-11-24-pipeline.json`)**, same
command as `-3.json` apart from date and note. The machine was quieter
than on 2026-11-23: Docker Desktop not running, no other agent building,
no flow collector; Defender and the search indexer ran as usual. So the
two runs differ in machine load as well as code, and the share of each
in the change is not separated.

- Capacity 1.9 million events/s, 2.4 times the 2026-11-23 runs and 1.5
  times the mimalloc run. The single-threaded reference engine ran at
  778,743 events/s (was 477,429 to 530,847); it still builds fresh
  outputs per event, but its patterns no longer allocate.
- p99 stays at 4 to 13 µs up to 90% load for even arrivals and 5 to 28 µs
  for Poisson. No step's p99 reached a millisecond (before: most 80% and
  90% steps did).
- Stalls are rarer but not gone: in 5 of 20 load steps the maximum
  reached 0.42 to 4.1 ms (p99.9 0.19 to 2.7 ms), with the feeder lagging by as much
  (`feeder_max_lag_us` up to 3,705), at 70% to 90% load. Which stage
  stalls is still not established. `pool_waits` was 0 in every step, so
  the item pool never ran dry.
- **With Docker Desktop running (`2026-11-24-pipeline-2.json`)**, at
  Evan's request: same code and command, with his live Wazuh stack and
  the oracle container idling (about one core between them, by `docker
  stats`; started 5 minutes before). Medians stayed at 1.4 to 5.9 µs and
  capacity at 1.84 million events/s, but p99 went to 0.3 to 64 ms from
  60% load up, with stalls up to 68 ms; in every step the feeder's lag
  matches the worst latency. So the Docker Desktop VM is the main source
  of the stalls seen here, on 2026-11-23 too (the VM's virtual CPUs on
  the pinned stage cores is the likely mechanism; inferred, not
  traced). Evan's instruction was to widen R5 to 3.5 if the result was
  still close to 3.16; it was not, so R5 stays at 3. R5 runs on this
  machine need Docker Desktop stopped, or the stage cores kept from the
  VM.
- Poisson at 90% has p99 22 to 28 µs, about 40 to 55 times the mean time
  per event at capacity (0.52 µs). A queue fed by Poisson arrivals at
  90% of its capacity has a mean wait of several service times and a
  p99 of tens, with no stall at all (M/D/1 queueing theory; not measured
  separately here), while at 50% its p99 is a few. So a ratio of at most
  3 may not be reachable for Poisson arrivals at 90% whatever the engine
  does. This bears on open question 1.

- **At normal priority the pipeline is not usable for tail latency here**:
  p99 at 50% load is 0.3 to 13 ms (p50 3 to 5 µs).
- **At time-critical priority, p99 holds at 6 to 20 µs up to 70% of
  capacity** in the sweep (one Poisson step at 60% reached 344 µs), and
  goes to milliseconds at 80% (all four steps, 1.3 to 2.8 ms). At 90%, two
  of four steps were in milliseconds and two stayed at 61 and 74 µs. R5
  needs 90%.
- **The ms tails come from stalls, not from queueing**: whenever p99 is in
  milliseconds, the feeder found the links full (`input_full_waits` > 0)
  and its own lag (`feeder_max_lag_us`) matches the worst latency. Some
  stage stopped for several milliseconds and back-pressure filled all four
  links (1,024 slots, about 1.3 ms at 780,000 events/s). Which stage, and
  why, is not established.
- **The allocator experiment**: with mimalloc, capacity rose 1.6× (about
  1.26 million events/s) and the reference engine 1.4× (752,490 events/s),
  so allocation is a large part of the cost. The stalls did not go away
  (ratios 415 to 2,100). So the system heap's lock alone does not explain
  them. Candidates left: preemption or interrupts on a machine that is not
  quiet and cannot isolate a core, page faults or OS calls inside the
  allocator, the Docker VM sharing the cores. Inference, not measured.
- Capacity varies 593,899 to 784,094 between runs of the same build with
  the system allocator; the machine load changed during the evening
  (another agent's builds, the Docker VM).
- The single-threaded reference engine ran at 477,429 / 504,821 / 530,847
  events/s (system allocator, three runs); the four-stage pipeline's
  capacity in the same run file is 1.2 to 1.5 times that.

## Deviations and corrections

- **Four stages, no route stage, one match worker.** SPEC §5 draws route
  and N match workers; those belong to R7 (M3).
- **Items are moved by value through the links, not handles to pooled
  blocks** (SPEC §5). The event, decoded fields and outcome are owned
  strings built by the reference engine's code, which is why decode and
  match allocate. Making them allocation-free (offsets into the line,
  reused field tables, no owned `String`s) is the R8 work that remains.
- **Reject reasons are rulelanes' own** (`empty`, `too_long`, `not_utf8`,
  `unknown_source`). `max_line` defaults to 65,536 bytes; Wazuh's own
  limit was not checked against the oracle.
- **Idle stages always spin** (the `stagelanes` behaviour); there is no
  back-off mode as in flowlanes.
- **Latency includes the feeder's lateness**: it is measured from the
  scheduled arrival time, so a feeder held back by a full link counts
  against the pipeline, as it should under R5.
- **`analysisd` was driven through its local socket**, not through
  syslog or logcollector, and its counters come from the state file
  (documented in Wazuh's "Standard Wazuh message format" and
  "wazuh-analysisd.state" pages). Its alert output stayed on.
- **The oracle reports `WAZUH_REVISION="rc2"`** next to `v4.14.10`
  (`wazuh-control info`). Recorded in the run files; not investigated.
- **The `analysisd` runs left about 650 MB or more of alerts** in the
  oracle container's `/var/ossec/logs/alerts/` (647 MB measured after the
  trial runs; two more 20 s runs followed). Not deleted.

## Open questions for Evan

1. **Arrival pattern for R5**: decided by Evan 2026-11-24: evenly spaced
   arrivals, applied to past runs too (SPEC R5 updated). Poisson is still
   measured and published. Against the rule, every run fails: the
   2026-11-23 runs (even ratios 5.2 to 2,100) and
   `2026-11-24-pipeline.json` (2.16 passes, 3.16 fails; one of two
   repeats).
2. **Capacity for R5**: the unpaced capacity is a peak. Should R5 use the
   highest rate that holds without stalls instead, or keep 90% of the
   unpaced figure?
3. **R6 method**: is the local-socket method acceptable as a first
   figure, or should both engines take syslog over UDP? Should
   `analysisd`'s alert files stay on (fair to its real use) or go off
   (fair to rulelanes' in-memory sink)?
4. **Allocator**: mimalloc raised capacity 1.6×. Use it in the engine's
   binaries, or treat zero allocation (R8) as the only answer? It is an
   off-by-default bench feature now.
5. **Oracle alerts** (650 MB+ from these runs): delete them?
6. **Normal priority** made the tails unusable here (ms at 50% load). Is
   time-critical acceptable as the default for stage threads on Windows?
7. **PCRE2 engine** (new, 2026-11-24). fancy-regex builds a capture set
   on every match, so a decoder regex written as PCRE2 allocates per
   event; that is now most of what decode allocates. Options:
   a. keep fancy-regex and accept it (0.22 allocations per event on this
      corpus; more on a ruleset with more PCRE2 decoders);
   b. the `pcre2` crate, bindings to the PCRE2 C library that Wazuh itself
      uses (bindings MIT OR Unlicense, library BSD-3-Clause, both GPL-3.0
      compatible; licences from memory, to check). It reuses match data
      across calls, and matches would be PCRE2's own, not an imitation,
      which could only help R1. Cost: a C library built with `cc`, as the
      mimalloc feature already does;
   c. for PCRE2 patterns without look-around or backreferences, run
      `regex-automata` directly with a per-stage cache, and keep
      fancy-regex for the rest. Allocation-free for those patterns only,
      and a third engine whose results must equal fancy-regex's.
   Recommendation: b, checked against the oracle with R1 before it
   replaces fancy-regex.
8. **R5 rule for Poisson arrivals**: answered with question 1 (evenly
   spaced only).
